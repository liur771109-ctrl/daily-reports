## 四、业务模式分析

### 1. 核心特点："多厂商整合者"加"自研产品化"
- **传统强项**：作为海外 IT 产品的代理商和整合商（OutSystems、Pendo、OpenLegacy、Aitomatic、Dynamo AI、Google Cloud、UiPath 等），把海外技术快速引进日本金融机构，并做本地化。
- **新的动向**：开始推出**自有产品和 SaaS**，例如 C-NOAH、C-FAPI、C-CodeBlossom、Security Steward，从"承包项目"转向"**提供平台和产品**"，以提高利润率和客户黏性。

### 2. 在价值链上的位置
- **不做核心账务系统本身**，那是 NTT Data、富士通、日立、日本 IBM 等的领域。
- 主攻**核心系统周边和上层**：用 API 解放遗留系统、前端渠道、数据和 AI、安全、云基础设施。
- 战略含义：核心系统现代化（OpenLegacy 用 API 把核心系统包装起来）和 AI Ready 化（瑞穗案例），恰好落在"**核心系统和 AI 应用之间的连接层**"。随着 AI 普及，这一层的价值会越来越高。

### 3. SWOT（供论文参考）

| 优势（S） | 劣势（W） |
|---|---|
| 多厂商整合和海外技术的引进能力 | 不做核心账务系统，在大型核心系统更新项目里难当主承包商 |
| 全价值链服务，加上自有数据中心 | 金融收入规模（约 700 亿日元）远小于 NTT Data 等专业金融 SIer |
| 市场类、风险类系统的开发能力 | 地方银行属于其他板块，金融事业组主要面向大型机构 |
| 已有瑞穗、三菱 UFJ 等大型银行的 AI 实绩 | 自有产品还在起步，C-NOAH 的采用案例没有公开 |

| 机会（O） | 威胁（T） |
|---|---|
| 金融机构 AI 使用率快速上升（日本银行调查：约 3 成→约 5 成→约 8 成） | 大型银行推进 AI **内部化**（金融厅讨论文件 1.1 版有记载） |
| 核心系统上云和现代化的需求 | 金融机构担心依赖供应商、知识产权外流，会要求知识产权归属于自己 |
| 金融厅鼓励面向客户的 AI（安全港、风险分级） | OpenAI、Google 等平台方直接接触金融机构（例如福冈 FG 与 OpenAI 直接合作） |
| 地方金融机构 AI 支援政策（令和 7 年度补正预算） | 咨询公司（NRI、埃森哲等）也在争夺 AI 上游 |

## 五、与论文主题的连接（金融厅、日本银行趋势 × CTC 的应对）

| 监管和行业趋势 | 出处 | CTC 金融事业组的应对 |
|---|---|---|
| 数据整备是 AI 的前提（"Garbage in, Garbage out"） | 金融厅讨论文件 1.1 版 IV-①-i | 瑞穗的 AI Ready 化项目、C-CodeBlossom |
| 遗留系统和 Excel 业务阻碍 AI | 金融厅讨论文件 1.1 版 | 遗留系统现代化（OpenLegacy API 化） |
| 幻觉是面向客户 AI 的最大课题，需要多层护栏 | 金融厅讨论文件 1.1 版 Box 4 | C-NOAH 引入 Dynamo Guard 抑制幻觉 |
| 面向客户的 AI 开始萌芽（呼叫中心等） | 金融厅讨论文件 1.1 版 III-3 | 三菱 UFJ 的下一代联络中心构想 |
| 安全和 API 连接点可能成为安全漏洞 | 金融厅讨论文件 IV-①-vii、viii | Security Steward、C-FAPI |
| 依赖供应商、知识难以留在内部、内部化趋势 | 金融厅讨论文件 IV-①-iv、vii | **对 CTC 是挑战**：要从"代为开发"转向"支援内部化"，例如瑞穗案例中共享 400 多条提示词 |
| 使用从一般事务扩展到核心业务 | 日本银行 2026 年度调查 | 核心系统连接层（API 化、AI Ready 化）的需求上升 |

**论文可用的论点**：在日本金融业的 AI 化中，CTC 这类多厂商 SIer 的角色正在从"系统承包商"转变为"**连接核心系统与 AI 的中间层建设者**"和"**海外 AI 技术的本地化引进者**"。但金融机构的内部化趋势和对知识产权的诉求，也在倒逼 SIer 改变商业模式，从交付系统转向转移能力、提供平台。
